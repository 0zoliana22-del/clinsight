# 合规红线清单（医疗 AI）

> **一句话前提**：这份清单是产品侧的**风险提示与工作清单**，不是法律意见，也不能替代医院法务/法规部门。
> ClinSight 把这句话写进了代码输出里（`compliance.disclaimer`），因为它自己也得守这条边界。

---

## 一、六条红线

红线 = 越过去，产品性质就变了（从工具变成诊疗行为），不是"加个免责声明"能解决的。

| ID | 红线 | 为什么不能碰 | 怎么落到产品里 |
| --- | --- | --- | --- |
| **RL-01** | 不输出诊断结论、处方、剂量建议 | 一旦输出可执行的治疗决策，就从"辅助工具"变成"诊疗行为"，责任主体变了 | 输出只给"证据 + 选项 + 出处"，结论由医生下；界面上明确"本工具不提供诊疗建议" |
| **RL-02** | 患者数据不出院、不入公网模型 | 病历属敏感个人信息，出境/出院的合规成本极高 | 优先私有化/专有云；确需外部模型时先脱敏，且只传任务必需字段 |
| **RL-03** | 先判定是否按医疗器械管理 | 用于诊断、治疗、监护、决策支持的 AI 软件通常按二类/三类器械管理 | 立项第一周就开界定会，结论书面留档并写进 PRD 附录 |
| **RL-04** | AI 输出必须可追溯、可复核 | 不可回放就无法划分责任，也无法处理投诉 | 记录生成时间、模型版本、输入摘要、引用出处、确认人；支持按患者回放 |
| **RL-05** | 涉及人的研究必须伦理审查 | 即便只是"效率对比"，只要用于科研/发表就要过伦理 | 用途边界写清楚；科研用途单独走伦理，不混在工具迭代里 |
| **RL-06** | 不做"没提示 = 没问题"的默认承诺 | 提示类功能一旦被当成安全网，漏报的后果由产品承担 | 明示覆盖范围与漏报可能；漏报率作为一级指标，优先于误报率 |

**最容易忽略的是 RL-06。** 一个交接提醒功能，上线三个月没人报警，护士就会默认"系统没响就是没事"。这时候一次漏报，责任在产品不在护士。所以提示类功能的说明书里必须有一句："本功能仅覆盖 X 类信息，不能替代床边评估。"

## 二、八项检查（ClinSight 的 `CK-01 ~ CK-08`）

立项到上线之间，这八项必须逐项关闭。代码里会给每项打 `pass / fail / unknown`，**`unknown` 不等于通过**。

| 编号 | 检查项 | 通过标准 | 常见坑 |
| --- | --- | --- | --- |
| CK-01 | 数据处理合法性基础 | 有院内数据使用授权；患者知情同意覆盖使用范围 | 用"科研用途"的授权做产品功能 |
| CK-02 | 脱敏与最小必要 | PHI 字段清单 + 入模前脱敏规则 | 只脱姓名，忘了病历号/住院号/日期+科室可反推身份 |
| CK-03 | 部署形态 | 数据流向图 + 模型部署位置明确 | "先用公网 API 试试"，试完就上线了 |
| CK-04 | 器械属性判定 | 法规同事书面结论 | 觉得自己是"效率工具"就不判，出事才发现是二类 |
| CK-05 | 人审与留痕 | 确认点不可跳过 + 审计日志字段齐全 | 做了"确认"按钮，但可以一键全选通过 |
| CK-06 | 输出边界说明 | 固定位置声明覆盖范围与不确定性 | 免责声明放在设置页第 4 层，等于没有 |
| CK-07 | 伦理审查 | 科研/发表/对照实验前完成送审 | 用真实数据做 A/B，没走伦理 |
| CK-08 | 不良事件与回滚 | 上报路径 + 灰度回滚开关 | 只能全量上线，出问题只能停机 |

## 三、风险分级与门禁

ClinSight 按访谈内容自动判级，直接影响"能不能进开发"：

| 等级 | 触发条件 | 门禁 |
| --- | --- | --- |
| **高** | 出现诊疗决策、辅助诊断、高危筛查等表述 | **暂不进入开发**：先完成器械属性判定 + 人审设计评审 |
| **中** | 涉及 PHI、患者端交付，或含安全类需求 | 可进入**原型验证**：脱敏方案与边界说明必须先于真实数据接入 |
| **低** | 纯效率/信息类，无患者标识 | 可进入开发：保持人审留痕 |

**注意"中"这一档的措辞**：不是"可以做"，是"可以用假数据做原型"。真实数据接入是另一个关卡。

## 四、五个真实项目里最容易踩的坑

### 1. 把"辅助决策"说成"信息展示"
"我们只是把风险评分显示出来，医生自己判断"——评分本身就是决策支持。判断标准不是"有没有给建议"，而是"医生会不会照着做"。

### 2. 用否定句骗过合规扫描
"本系统不提供诊断建议"这句话里有"诊断"。ClinSight 专门做了否定句识别（`compliance.mentions`），因为**人工评审也会被这种句子骗**。

反过来，疑问句不能当否定："这个算不算辅助诊断？"——这是在问边界，风险信号更强。

### 3. 脱敏只脱了显式字段
姓名、身份证好脱；**日期 + 科室 + 罕见病**组合起来就能定位到人。最小必要原则要按"可重识别风险"判，不是按字段名判。

### 4. 把免责声明当成免责
声明的作用是"让用户知道边界"，不是"出了事我不负责"。真正起作用的是：人审点设计、可回放日志、漏报率的量化。

### 5. 合规最后才介入
合规评审排期通常 2~4 周。开发完才送审，等于把工期赌在评审结论上。**正确做法：立项第一周就拉法规同事进群，用一页纸说清"给谁用、输出什么、数据从哪来"。**

## 五、边界声明（工具能做什么 / 不能做什么）

**能做：**
- 在写 PRD 之前，把访谈里出现的风险信号标出来；
- 给出一份可执行的自查清单和需要补的材料；
- 让"合规"成为需求评审的一部分，而不是上线前的关卡。

**不能做：**
- 判定产品是否属于医疗器械（这是法规部门的职权）；
- 替代伦理审查；
- 给出法律结论；
- 覆盖所有风险——词表命中的是**已定义的模式**，没命中不代表没风险。

> 最后一条要写进产品说明。一个风险扫描工具最大的风险，是让用户以为"扫过就没问题了"。
