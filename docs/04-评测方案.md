# 评测方案

> 一个没有评测的 AI 产品，迭代靠的是"感觉这次好多了"。
> 这个项目在写第二行业务代码之前，先把金标集和评测脚本搭好了。

---

## 一、评什么：三层，三个不同的问题

| 层 | 问题 | 指标 | 谁关心 |
| --- | --- | --- | --- |
| 抽取 | 该发现的需求，发现了吗？ | 召回 / 精确率 | 产品 |
| 排序 | 重要的事情，排在前面了吗？ | 优先级命中率 | 产品 + 业务方 |
| 合规 | 该拦的风险，拦住了吗？ | 风险召回 | 合规 |

三层必须分开测。混成一个"准确率"的后果是：抽取漏了一半，但因为排序看起来还行，总分依然好看——问题被平均数吃掉了。

---

## 二、金标怎么建

### 流程

1. **读访谈全文**，人工写出"如果我是这个产品经理，会提哪些需求"；
2. 每条需求标注：`名称 + 匹配关键词 + 期望优先级`；
3. **不看工具输出**——先写金标，再跑工具，顺序反了就是自我实现；
4. 第二个人独立标一遍，分歧处讨论到一致（当前版本尚未做双标，这是 v0.2 要补的）。

### 标注规范

- **粒度**：一条金标主题 = 一条可独立排期的需求，不是一句抱怨；
- **匹配词**：用**能唯一定位这条需求**的词，不用"效率""数据"这种高频泛词，否则精确率会虚高；
- **优先级**：按"如果只能做三件，做不做它"来标，不按"重不重要"标。

### 切分

| 数据集 | 样本 | 用途 |
| --- | --- | --- |
| dev | INT-001 心内科 / INT-002 呼吸科 / INT-003 内分泌科 | 调词表、调权重、校准阈值 |
| test | INT-004 急诊 / INT-005 儿科 / INT-006 骨科 | **只跑不改**，代表泛化能力 |

写 test 时词表已经冻结，一个字都没回头改。这是这份报告里唯一值得信的部分。

## 三、指标定义

设金标主题集合为 $T$，生成需求集合为 $R$。

**需求召回**（主题被覆盖的比例）
```
recall = |{t ∈ T : ∃r ∈ R, r 命中 t 的匹配词}| / |T|
```

**需求精确率**（生成的需求里，有多少是真的）
```
precision = |{r ∈ R : r 命中任一 t 的匹配词}| / |R|
```

**优先级命中率**（排序是否达到期望）
```
优先级序：Must=3 > Should=2 > Could=1 > Won't=0
hit(t) = 1  当且仅当  覆盖 t 的需求里最高等级 ≥ t 的期望等级
```
这里刻意让"做多了"不算错：期望 Should 但实际排了 Must，算命中（过度投入但不致命）；期望 Must 却只排了 Should，算未命中（真正的排序失误）。

**风险召回**
```
flag_recall = |期望风险项 ∩ 检出的风险项| / |期望风险项|
```

## 四、当前结果（v0.1 规则版）

```
ID        split  themes  reqs  recall  prio   prec
INT-001   dev         5     5   1.00   1.00   1.00
INT-002   dev         5     6   1.00   0.80   1.00
INT-003   dev         3     3   1.00   1.00   1.00
INT-004   test        6     4   0.67   0.67   0.75
INT-005   test        5     3   0.60   0.60   1.00
INT-006   test        5     1   0.40   0.40   1.00
--------------------------------------------------
DEV                  13    14   1.00   0.92   1.00
TEST                 16     8   0.56   0.56   0.88
```

### 怎么读这组数

- **dev 的 1.00 是过拟合**，没有讨论价值。它只证明"词表能覆盖我写过的样本"，这是循环论证。
- **test 的 0.56 才是基线**。一个规则系统在没见过的科室上召回一半，符合预期——它本来就不是为了通用而设计的。
- **精确率高（0.88）而召回低**，说明系统"说少但说得准"。这是刻意的：在需求评审场景里，漏掉一条还能靠人补，编出一条假需求会浪费一个迭代。

**这个取舍要写清楚**：如果场景换成"风险筛查"，召回低就是致命的，权重必须反过来。

## 五、失败模式归因（比总分更有用）

把 test 集的漏检逐条看，归成 4 类：

| # | 模式 | 例子 | 能否用规则修 | 修法 |
| --- | --- | --- | --- | --- |
| 1 | **隐喻/口语没有词表对应** | 急诊"从一百个里把这几个人挑出来"= 分诊 | 勉强 | 加同义词表，但每加一批就过拟合一批 |
| 2 | **一句话里两个痛点只取一个** | "抢救记录事后补 + 时间点靠估" | 不能 | 需要 span 级抽取，规则做不到 |
| 3 | **缺少"流程协调"类别** | 骨科"排期撞车"既不是效率也不是信息 | 能（补类别） | 但类别是有限的，场景是无限的 |
| 4 | **领域术语不在表里** | "危急值""耗材""手术排期" | 能（补词） | 同上，永远补不完 |

结论很清楚：**模式 1/3/4 可以靠堆词表缓解，模式 2 结构上做不到。** 这就是换 LLM 抽取的依据——不是为了"更先进"，是因为规则在"一句话多个意图"上有硬上限。

## 六、v0.2 实验设计

### 三组对照（同一 test 集，同一金标）

| 组 | 抽取 | 排序 | 合规 |
| --- | --- | --- | --- |
| A（现状） | 规则 | 规则 | 规则 |
| B | LLM（结构化输出 + schema 校验） | 规则 | 规则 |
| C | LLM 抽取 + 规则兜底（并集去重） | 规则 | LLM 初判 + 规则兜底 |

**排序和合规始终保持规则主导**——它们要能当场复算、要能审计。只让模型做"理解语言"的部分，不让它做"承担责任"的部分。

### 验收门槛

- B 组 test 召回 ≥ 0.80（相对基线 +0.24），精确率 ≥ 0.80；
- B 组单份访谈耗时 ≤ 8 秒，单份成本 ≤ ¥0.05；
- C 组召回不低于 B，且**规则兜底仍能单独跑通**（断网可用）；
- 任何一组如果精确率低于 0.75，不上线——宁可漏，不可编。

### 评测方法上的两个坑

1. **不要用 LLM 打分来评 LLM 输出**：评判者和被评判者是同一个模型，会系统性偏好自己的表达；
2. **不要只看平均分**：必须看逐条漏检。0.56 的召回里，如果漏的全是"安全类"，那平均分毫无意义。

---

## 七、一句话总结

评测集的价值不在于那个分数，而在于**它把"这次改得好不好"从主观判断变成了可复现的对比**。

有这组数，换模型是实验；没有这组数，换模型是赌博。
