# ClinSight 自己的 PRD

> 用项目自己的方法论，给项目自己写一份 PRD。这不是炫技——如果一个需求洞察工具连自己的需求都说不清楚，它没有资格处理别人的。

**版本** v0.1 ｜ **状态** 已实现（MVP） ｜ **作者** 产品

---

## 0. 一页结论

- **一句话**：把临床访谈从"几十页口语"压缩成"可验证、可排序、可评审的需求清单"，并同步给出 AI 能力边界与合规红线。
- **第一版切口**：只做"信息检索类"需求（证据最足、可行性最高、合规风险最低），不做诊疗决策类。
- **不做什么**：不做 EMR 集成、不做自动写入、不做诊断、不做全自动需求生成。
- **成功标准**：一份 40 分钟访谈，PM 从"整理 2 小时"降到"评审 20 分钟"。

---

## 1. 背景与问题

作者在医疗 AI 项目中反复看到同一个断层：**访谈里全是信息，PRD 里全是结论，中间没有可审计的转换。**

具体三个症状：

| 症状 | 现场长什么样 | 后果 |
| --- | --- | --- |
| 需求不可验证 | PRD 写"提升医生效率" | 上线后无法判断成功与否，只能靠满意度打分 |
| 优先级不可解释 | "这个重要，先做" | 被问"凭什么"时答不出，资源被嗓门大的人拿走 |
| 合规后置 | 开发完才送审 | 返工 1~3 个月，或直接废弃 |

**根因不是能力问题，是缺少中间产物。** 从原话到需求的转换过程留在 PM 脑子里，既不能被评审，也不能被复用。

## 2. 目标与非目标

### 2.1 目标

- 每条需求 100% 可回溯到原话（轮次级）
- 每个优先级判定可当场复算（因子级）
- 合规风险在写 PRD 之前暴露（检查项级）
- 单份访谈端到端 < 1 秒（规则模式），离线可用

### 2.2 非目标（明确不做）

- ❌ **不做全自动需求生成**：工具的定位是"结构化草稿"，最终判断必须是人
- ❌ **不做 EMR / HIS 集成**：v0.1 只吃导出文本，集成是 v0.3 之后的事
- ❌ **不做诊疗建议**：红线，见 [合规清单](03-合规红线清单.md)
- ❌ **不做多模态**（录音转写、影像）：转写是成熟能力，先用现成工具
- ❌ **不做协作与权限**：单人使用，先把单点价值验证清楚

## 3. 用户与场景

| 用户 | 场景 | 他现在怎么做 | 他真正要的 |
| --- | --- | --- | --- |
| **AI 产品经理**（主用户） | 访谈后 24 小时内出需求清单 | Word 里贴录音稿，手动标黄，凭记忆归类 | 别漏、别编、能解释 |
| **科室主任**（评审者） | 需求评审会上质疑优先级 | 听 PM 讲，凭经验判断 | 看到证据和算法，而不是结论 |
| **合规 / 法规**（门禁） | 立项评审 | 事后看方案，逐条问 | 早期就知道风险在哪，别等做完 |

**核心场景**：PM 访谈完一位医生，当天要把结论带进评审会，并且**经得起医生当场质疑**。

## 4. 需求清单（MoSCoW）

| ID | 需求 | 优先级 | 依据 |
| --- | --- | --- | --- |
| R1 | 访谈文本 → 痛点簇，每条挂原话与轮次 | **Must** | 没有证据链，整个产品失去存在理由 |
| R2 | 痛点 → 需求条目，带可证伪的验收信号 | **Must** | 这是"洞察"和"需求"的分界线 |
| R3 | MoSCoW 加权排序，因子级归因 | **Must** | 直接对应"优先级不可解释"这个根因 |
| R4 | 合规风险分级 + 检查清单 | **Must** | 后置合规的返工成本最高 |
| R5 | 生成可评审的 PRD（Markdown） | **Must** | 交付物，否则结论无法流转 |
| R6 | 用户自述优先级 vs 模型排序的一致性校验 | **Should** | 防止工具悄悄覆盖用户判断；成本低、价值高 |
| R7 | AI 可行性评估（能做/不能做/人审点） | **Should** | 避免把"做不到"排进 Must |
| R8 | 科室知识包（场景 × 类别的方案卡片） | **Should** | 决定输出"像人话"还是"像模板" |
| R9 | 金标集与自动评测 | **Should** | 没有它，每次迭代都是拍脑袋 |
| R10 | Web 演示界面 | **Could** | 评审时比终端输出有说服力 |
| R11 | LLM 润色陈述 | **Could** | 规则模板已经够用；模型只做语言层 |
| R12 | 多访谈聚合（一个科室 5 份访谈合并去重） | **Won't**（本期） | 单份验证清楚之前，聚合只会放大噪声 |
| R13 | 录音直接转写 | **Won't**（本期） | 现成工具可替代，不是差异化 |

## 5. 方案

```
                 ┌──────────────┐
   访谈 JSON ───▶ │  ① 抽取       │ 场景×类别聚类，证据累积
                 └──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  ② 转译       │ 模板 + 科室知识包 → 需求陈述
                 └──────┬───────┘
              ┌─────────┴─────────┐
              ▼                   ▼
      ┌──────────────┐    ┌──────────────┐
      │ ③ 可行性      │    │ ④ 合规        │
      │ 能力边界/人审  │    │ 8 项检查/红线  │
      └──────┬───────┘    └──────┬───────┘
              └─────────┬─────────┘
                        ▼
                 ┌──────────────┐
                 │  ⑤ 排序       │ 加权打分 + 安全底线
                 └──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  ⑥ 校验       │ 用户自述 vs 模型排序
                 └──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  ⑦ 交付       │ PRD + JSON
                 └──────────────┘
```

### 关键技术选择

- **规则优先，LLM 可选**：确定性内核保证可复算、可审计、离线可用；LLM 只做语言润色，失败静默降级。
- **知识层外置**（`taxonomy.py`）：词表、场景、科室方案卡、合规规则都是数据，PM 能改，不用发版。
- **零第三方依赖**：医院内网装不了包是常态，能跑起来比技术先进重要。

## 6. 取舍记录

| 决策 | 备选 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- | --- |
| 抽取用规则还是 LLM | A. 直接上 LLM | **规则** | 可复现、零成本、断网可用；且需要先有基线才知道 LLM 好在哪 | test 召回只有 0.56，明确不够用 |
| 痛点与需求是否合并 | A. 多条痛点合并成一条需求 B. 1:1 | **1:1** | 可追溯性优先：每条需求指回一个痛点簇，评审时不会"这条从哪来的" | 输出的需求数偏多，需要人工合并 |
| 排序是否让 LLM 参与 | A. LLM 直接排序 B. 加权模型 | **加权模型** | 要能当场复算；LLM 给不出稳定中间量，也无法审计 | 权重是人为设定的，需要持续校准 |
| 合规做深度还是广度 | A. 深挖器械注册 B. 覆盖 8 类常见风险 | **广度** | 产品的价值是"早期暴露"，深度判定属于法规部门 | 每类都不够深，需明确边界免责 |

## 7. 指标

**北极星**：需求条目在评审会上被采纳的比例（目标 ≥70%）。

| 类型 | 指标 | 当前 | 目标 |
| --- | --- | --- | --- |
| 效果 | test 集需求召回 | 0.56 | ≥0.80（v0.2 换 LLM 抽取） |
| 效果 | 需求精确率 | 0.88 | ≥0.80（不允许为了召回牺牲精确率） |
| 效率 | 单份访谈处理耗时 | < 1 ms | < 8 s（含 LLM） |
| 效率 | PM 整理时间 | 2 小时（人工基线） | ≤20 分钟 |
| 信任 | 证据可回溯率 | 100% | 保持 100% |
| 护栏 | 编造需求数 | 0 | 必须保持 0 |

**护栏指标比北极星更重要**：为了提升召回而编造需求，等于把工具变成噪声源。

## 8. 风险与开放问题

| 风险 | 应对 |
| --- | --- |
| 规则泛化差，新科室召回崩塌 | 用 LLM 抽取（评测集已就位，可直接对照）；科室知识包按科室补 |
| 输出被当成"结论"而非"草稿" | 界面固定位置标注"结构化草稿，需人工确认"；PRD 首页写明 |
| 合规提示造成虚假安全感 | 明确写"未命中 ≠ 无风险"，边界声明进产品 |
| 被质疑"这不就是个模板工具" | 用评测集和一致性校验回答：模板工具不会告诉你"你的排序和用户直觉冲突了" |

**开放问题**：
- 多份访谈如何聚合去重？（本期不解决，但会影响真实使用）
- 权重和阈值是否需要按科室个性化？
- 如果 LLM 抽取的召回上去了但精确率下降，接受阈值定在哪？
