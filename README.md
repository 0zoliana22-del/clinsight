# ClinSight · 临床需求洞察 Agent

[![CI](https://github.com/0zoliana22-del/clinsight/actions/workflows/ci.yml/badge.svg)](https://github.com/0zoliana22-del/clinsight/actions/workflows/ci.yml)

[![Dependencies](https://img.shields.io/badge/dependencies-0-brightgreen)](pyproject.toml)
[![License](https://img.shields.io/badge/license-MIT-lightgrey)](LICENSE)

> 把医生访谈里的口语化抱怨，变成**可验证、可排序、可交付**的需求条目，并同步给出 AI 能力边界与合规红线。

一个 AI 产品经理的作品集项目：不是"我做过需求分析"，而是**"这是我做的需求分析工具，你现在就可以跑一遍"**。

```bash
python run.py demo     # 6 份访谈 → 6 份 PRD，零依赖
python run.py web      # 打开演示界面（127.0.0.1:8765）
python run.py eval     # 在金标集上跑评测，输出真实指标
```

---

## 1. 为什么会想做这个

医疗 AI 产品最容易死在第一步：**需求是拍脑袋的**。

- 访谈记录是几十页口语，落到 PRD 就变成"提升效率""优化体验"，没人能验证；
- 需求优先级靠"领导觉得重要"，问一句"凭什么"就答不上来；
- 合规在开发完才介入，做出来发现属于二类器械，或者压根不能碰患者数据。

这三件事其实是同一个问题：**从"医生说的话"到"要做的功能"之间，缺一道可审计的转换**。

ClinSight 就是这道转换。它的输出不是"洞察"，是可回放、可复算、可评审的中间产物。

---

## 2. 它做什么：一条 7 步流水线

```
访谈 JSON
   │
   ├─① 抽取      口语 → 痛点簇（场景 × 痛点类别），每条挂原话
   ├─② 转译      痛点 → 需求条目（陈述 + 证据 + 可验证验收信号）
   ├─③ 可行性    能力边界：能做什么 / 不能做什么 / 人审点 / 评测指标
   ├─④ 合规      器械属性、PHI、决策支持、留痕…… 8 项检查 + 红线
   ├─⑤ 排序      MoSCoW 加权打分，每个因子都能当场复算
   ├─⑥ 校验      模型排序 vs 用户自述优先级，不一致就暴露
   └─⑦ 交付      PRD（含里程碑、风险、开放问题）+ 可下载 Markdown
```

**为什么做成显式的 7 步，而不是一个大 prompt？**
每一步的失败模式不同——抽漏了、判错了、排偏了——必须能定位到具体一步，才能分别优化和评测。把 Agent 做成黑盒，出事时你连从哪查都不知道。

---

## 3. 三个我认为最重要的设计决策

### ① 证据优先：没有原话，就没有需求

每条需求都带 `pain_ids → evidence[turn, speaker, quote]`。PRD 里能点回"第 7 轮，医生原话是这句"。

> 一条说不出出处的需求，就是一条不该被排期的需求。

### ② 排序可解释：MoSCoW 不是标签，是算术

| 因子 | 权重 | 含义 |
| --- | --- | --- |
| 严重度 | 25 | 出错后果有多重（安全类天然高） |
| 频次 | 15 | 每天 / 每周 / 偶尔 |
| 覆盖角色 | 10 | 只影响医生，还是医生+护士+患者 |
| 证据强度 | 15 | 有几个人反复提到 |
| AI 可行性 | 20 | 落在能力边界内的哪一段 |
| 成本效率 | 10 | 单位效果要花多少钱 |
| 合规风险 | −15 | **扣分而非否决**：多数需求不是不能做，是要付合规成本 |

现场被问"凭什么它是 Must"，可以逐项加给他看。

**例外：安全底线不参与降级。** 涉及患者安全且严重度 5 分的需求，哪怕算出来只有 58 分，也强制进 Must——排序模型可以告诉你"性价比低"，但不能替你决定"这条命可以不管"。真要砍，砍范围，不砍等级。

### ③ 不一致要暴露，不要悄悄覆盖

工具会检测访谈里"如果只能先做一个，您选哪个"的回答，再和模型排序对比：

- 一致 → `✅` 直接写进第一版范围；
- 不一致 → `⚠️` 摆出双方结论，说清可能是"用户的直觉被低估"还是"可解性撑不起"，**交给人裁决**。

在 `INT-002`（呼吸科护士长）上，这个机制真的抓到了冲突：护士长说最想解决**交接班**，模型按证据强度排出来第一是**宣教**。这个差异本身就是产品判断的材料，藏起来才是失职。

## 4. 评测：说数字，不说感觉

金标集是人工标注的"理想需求集"。刻意做了 **dev / test 切分**：`INT-001~003` 写词表时看过（会过拟合），`INT-004~006` 是词表冻结后才写的急诊 / 儿科 / 骨科访谈。

| 数据集 | 访谈 | 金标主题 | 生成需求 | 需求召回 | 优先级命中 | 需求精确率 |
| --- | --- | --- | --- | --- | --- | --- |
| dev（调过词表） | 3 | 13 | 14 | **1.00** | 0.92 | 1.00 |
| test（未见过的科室） | 3 | 16 | 8 | **0.56** | 0.56 | 0.88 |

**dev 的 1.00 不能拿来吹**，它只说明词表覆盖了我自己写过的样本。真正有意义的是 test 的 0.56。

失败案例已被定位成 4 类系统性问题（详见 [评测方案](docs/04-评测方案.md)）：

1. **隐喻识别不了**：急诊说"从一百个里把这几个人挑出来"，规则不知道这就是分诊；
2. **一句话两个痛点只取一个**："抢救记录事后补 + 时间点靠估"被迫二选一；
3. **没有"流程协调"这个类别**：骨科"排期撞车"既不是效率也不是信息，几乎全漏；
4. **领域名词不在表里**："危急值""耗材""手术排期"是标准临床术语，但词表按通用中文写的。

> 这四条就是 v0.2 换 LLM 抽取的直接理由。**没有这组数字，换模型是拍脑袋；有了这组数字，换完能证明好多少。**

### v0.2 对照实验：装置已就绪，表还空着

`extract_llm.py` + `ab.py` 已经写好，做的是**单变量对照**：只换抽取器，可行性、合规、排序、金标口径全部不变，这样涨的每一分都能归因。

```bash
export CLINSIGHT_LLM_KEY=sk-xxx     # 任意 OpenAI 兼容端点
python run.py ab                    # A 规则 / B 纯 LLM / C 并集，一次跑完
```

两条纪律写进了代码，不是写在文档里：

- **降级样本不进分母**：某份访谈没跑通（超时、没 key、输出不合格），它产出的其实是规则版结果。混进 LLM 的平均分，就会得到一张"看起来一模一样"的假表。
- **没跑通就显示"未运行"**：缺 key 时报告里写"未运行"并返回非零码，绝不生成数字。

> **为什么我没有直接贴 A/B 数字？**
> 金标是我自己标的。再由我去跑一遍抽取，等于带着答案考试——分数必然虚高，那是假证据，不是实验。
> 这张表必须由一个**不知道答案的模型**来填。装置在这里，命令在上面，任何人（包括面试官）都能自己验。

## 5. 已知局限（写在明面上）

- **抽取是规则版**，召回率在没见过的科室只有 0.56，不能当生产工具用；
- **痛点簇与需求是 1:1**，真实项目里多条痛点应合并成一条需求，这里为了可追溯性放弃了合并；
- **合规判断是提示不是结论**，产品侧没有资格替代法规部门，工具里也写了这句免责；
- **访谈数据是模拟的**，不含真实患者信息，也没有做临床有效性验证。

## 6. 快速开始

```bash
git clone https://github.com/0zoliana22-del/clinsight.git
cd clinsight
python run.py list                 # 看样本
python run.py analyze INT-002      # 单份分析，终端直接出结论
python run.py demo                 # 全量跑，写出 output/
python run.py eval                 # 金标评测
python run.py ab                   # v0.2 对照实验（需要 LLM key，缺 key 会明确报"未运行"）
python run.py web --no-browser     # 演示界面 http://127.0.0.1:8765
python -m unittest discover -s tests -v   # 32 个测试
```

**零第三方依赖**，Python ≥ 3.10 即可。不是懒得装包，而是医院内网的机器往往装不了包——一个需要 `pip install` 半小时才能演示的工具，本身就过不了"可交付"这关。

不想跑代码？直接看快照：[示例 PRD（心内科）](examples/PRD-INT-001.md)、[示例 PRD（内分泌科，高风险场景）](examples/PRD-INT-003.md)、[评测报告](examples/eval_report.md)。

**可选 LLM 润色**（不接也能跑，失败自动降级）：

```bash
export CLINSIGHT_LLM_KEY=sk-xxx
export CLINSIGHT_LLM_BASE=https://api.deepseek.com/v1
python run.py analyze INT-001 --llm
```

模型只负责"把话说顺"，**不参与抽取、排序和合规判断**——因为排序要能当场复算，合规要能审计，prompt 的随机性不能进入责任链。

## 7. 目录结构

```
clinsight/
├── run.py                    # 零依赖启动器
├── src/clinsight/
│   ├── models.py             # Interview → PainPoint → Requirement → Analysis
│   ├── taxonomy.py           # 知识层：词表 / 场景 / 科室方案卡 / 合规规则（PM 可直接改）
│   ├── extract.py            # ① ② 抽取与转译（规则版）
│   ├── extract_llm.py        # v0.2：LLM 抽取 + schema 校验 + 缓存 + 降级
│   ├── ab.py                 # v0.2：规则 / LLM / 并集 三组对照
│   ├── feasibility.py        # ③ 能力边界
│   ├── compliance.py         # ④ 合规（含否定句识别）
│   ├── prioritize.py         # ⑤ ⑥ 排序与一致性校验
│   ├── prd.py                # ⑦ PRD 渲染
│   ├── pipeline.py           # 编排
│   ├── evaluate.py           # 评测
│   ├── llm.py                # 可选润色，失败降级
│   └── web.py                # 标准库 HTTP 服务
├── data/interviews/          # 6 份模拟访谈
├── data/gold/                # 金标标注
├── examples/                 # 生成结果快照（不用跑代码也能看）
├── tests/                    # 32 个单元测试
├── web/index.html            # 单文件界面，无构建
└── docs/                     # 方法论 / PRD / 合规 / 评测 / 路线图 / 面试讲法
```

`taxonomy.py` 是刻意做成"显式词表"的：产品经理改词表就能适配新科室，不用等工程师。**知识库本身就是评审物**——哪些话算痛点信号，应该拉着医生一起校准。
